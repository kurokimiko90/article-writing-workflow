讓知識成為文章，
讓文章留下知識。

人類掌握內容方向與最終決策，AI Agent 負責分析、規劃、生成與品質檢查。從原始材料出發，完成有邏輯、易理解、引人入勝的文章，再依完成的文章製作圖片或 PPT，並保留可重用的知識。

00 / WHY

為什麼做這個：讓經驗先被確認，再被看見

經驗類內容的價值在人的想法與實戰經驗裡，但這些經驗通常散在筆記和記憶中，沒有被整理、沒有被驗證，也很難快速讓別人看懂。這個項目要解決的，就是從「我做過、我想過」到「別人看得懂、可以相信」之間的距離。

設計理念

  • 以人為基礎：內容的起點是人的想法與經驗；AI 不替人創造觀點，也不補造事實。
  • AI 輔助整理：AI 負責把零散材料整理成有結構、可追溯的知識。
  • 確認與優勢：AI 幫忙找出現有想法哪裡已站得住、哪裡還需要確認，以及其中值得被看見的優勢與啟發。
  • 客觀框架：用固定的診斷、編號與審核框架看內容，而不是憑感覺修飾。
  • 快速可視化：在客觀框架確認後，快速把內容變成看得懂的圖。

適合的內容

  • 經驗分享、工作復盤、專案心得等以親身經驗為核心的內容。
  • 作者有想法和經驗，但還沒整理成結構、也還沒驗證過的材料。
  • 需要讓別人快速看懂，並且經得起追問的內容。

不追求的事

  • 不由 AI 憑空生成觀點或故事。
  • 不以文采掩蓋證據缺口。
  • 不做行銷、SEO 或自動發布。
一句話：

以人的經驗為基礎，用 AI 和客觀框架確認它、找出它的價值，再快速把它可視化。

01 / OVERVIEW

三次人類決策，一份知識基準，文章先行

以一篇文章為一個工作單位。文章與圖片／PPT 共用同一份已確認的知識基準；知識稿經 G2 確認後先逐章畫成「知識圖解」（diagram-design）；故事主線落在知識稿確認過的「啟發與價值」，配圖在文章寫完後依全文製作；每一步都定義輸入、行動、產出及完成條件，讓修改可以追溯。

02 / TASK BRIEF

選項已備好，未填就用預設

只需提供原始材料，其餘可選填。每個選單保留「使用預設」並列出實際預設值；也可自行輸入。設定摘要不增加確認關卡，AI 可直接進入診斷。

  1. 採用順序：人類最新明確指示 → 材料中明確的任務資訊 → 通用預設。AI 推測的核心觀點仍須在第三階段確認。
  2. 僅追問關鍵缺口：主題無法辨識、重要事實衝突或公開範圍不明時，集中提問；可獨立完成的工作繼續。
  3. 相關欄位才生效：選擇僅文章時停用視覺設定；選擇 PPT 才啟用簡報欄位。
  4. 變更可追溯：記錄新設定及受影響的段落、圖片、投影片；修改設定不等於批准新的事實。
原始材料與補充資訊
原始材料沒有預設內容。未提供時可先匯出任務設定，開始診斷前仍需補上材料。
預設：未附來源；影響結論的主張需查證。
預設：不模仿特定作者；保留清楚、有辨識度的原始表達。

設定只在本次開啟期間保留；重新整理會恢復預設。下載簡報可保存本次選項及材料。

03 / EXECUTION
九階段完整工作流
各階段完成後保留產出及狀態。G1、G2、G3 是需要人類明確決策的節點；等待決策時，可先整理已確認資料，不繼續依賴未批准內容的生成工作。


01
人類輸入 · AI 整理
建立寫作任務包
讓 AI 理解寫給誰、解決什麼問題，以及哪些素材可以使用。
輸入與執行
  • 人類提供草稿、經驗、研究資料、想法或案例，選填任務設定。
  • AI 保存原始材料，依來源分配 M01、M02 等素材編號。
  • 提取任務要求，缺少設定套用預設；標記人類指定、材料明確資訊與預設的來源。
  • 分開列出開始前必須補充的資訊與可在後續補充的資訊。
產出
  • 寫作任務簡報：讀者、目的、渠道、篇幅、風格與交付形式。
  • 素材目錄：編號、名稱、來源、日期、摘要及公開限制。
  • 待補充清單：缺口、影響及下一步。
完成條件：材料足以辨識主題與文章目的，任務設定有可執行值，原始材料保留完整。沒有材料時停在待輸入狀態。


02
AI 分析
內容分析與診斷
先判斷論點是否成立，再考慮如何寫得吸引人。
檢查面向檢查問題
事實與證據數據是否有來源？案例能否支持結論？資料是否過時？來源是否適用？
論證邏輯前提是否成立？是否混淆相關與因果？是否過度概括或忽略反例？
概念與表述關鍵詞是否有定義？前後用法是否一致？是否存在模糊敘述？
讀者理解是否缺少背景、例子、步驟或必要解釋？術語是否過多？
內容價值哪些是獨特觀點？哪些可深化？哪些重複、偏離目的或證據不足？
執行方式
  • 拆分主張 C01、證據 E01、案例 K01；連回素材來源。
  • 標記事實、作者經驗、推論與待確認主張。
  • 診斷問題分為高、中、低優先級；提出具體改法。
  • 依查證設定補充來源；無法驗證時保留不確定狀態。
產出
  • 簡潔診斷表、問題清單、改善方案。
  • 主張與證據清單、資訊缺口清單。
  • 值得深化的觀點及建議新增材料。
診斷示例 D01
原文：「這套方法大幅提高效率。」
問題：效率未定義，缺少前後比較。
影響：讀者無法判斷成果。
處理：補充可核對的耗時紀錄；若沒有紀錄，改為限定情境的經驗描述。
優先級：高｜狀態：待作者回覆。
完成條件：核心問題都有處理方案，未知內容已標記，診斷能對應到具體原文或材料。


03
人類決策 · G1
評論、補充與方向決策
人類集中處理方向與關鍵問題，AI 負責把問題變成可決定的選項。
AI 提交
  • 核心觀點候選與文章目的。
  • 問題 → 建議方案 → 影響 → 需要人類決定或補充的內容。
  • 優先呈現核心論點、關鍵事實與素材取捨。
  • 評論彼此衝突時指出衝突，交由人類決定。
人類決策選項
  • 保留：內容正確且重要。
  • 修正：調整事實、立場或表述。
  • 深化：補充案例、證據或解釋。
  • 刪除：重複、不相關或不宜公開。
  • 待確認：資訊不足，暫不定論。
產出：決策紀錄，包括問題編號、人類決定、理由、補充材料及日期。未回覆的關鍵決策保持待確認，不以預設代替批准。
完成條件：文章方向與高優先級問題已有明確決定，剩餘缺口有處理方式。未完成則回到 02 補充診斷或等待關鍵回覆。


04
AI 優化
整合評論，形成知識稿
將材料整理為可核對的知識基礎，先確保準確與清楚。
執行
  • 整合人類補充資料，修正事實與概念。
  • 合併重複內容，拆分混在一起的論點。
  • 為主張補上證據、案例、適用條件與限制。
  • 移除已決定刪除的內容，保留可追溯紀錄。
  • 逐項核對 D 編號是否已完成、待確認或不採用。
  • 提煉「啟發與價值」：核心啟發、新理解、張力與代價、可遷移做法、適用前提、建議故事主線；每條標依據編號及作者原話／AI 推論，不超出證據。
產出
  • HTML 基礎知識稿 knowledge-base.html（含啟發與價值），同步維護 knowledge-base.md；採分類標題＋分點條列，最多兩層。
  • 修改摘要：改了什麼、為什麼、對應哪項決策。
  • 待確認事項：缺口、原因與對後續寫作的影響。
  • 穩定的 C／E／K 編號及來源對照。
完成條件：所有評論都有處理結果，核心內容具備證據或明確的經驗／推論標記，「啟發與價值」各條可對應到編號。新衝突回到 03 決策。


05
人類確認 · G2
核定可信賴的知識基準
後續文章、圖片與 PPT 都以這份基準為依據，避免故事化時改變原意。
AI 提交確認包
  • 文章目的、核心觀點與主要主張。
  • 主張對應的證據、來源與日期。
  • 案例背景、過程、結果與可公開範圍。
  • 適用條件、限制、反例與待確認內容的處理方式。
  • 啟發與價值：讀者為什麼值得讀、讀完能帶走什麼，以及建議的故事主線。
人類確認清單
  • 符合自己的真實想法與立場。
  • 事實、數據及案例準確。
  • 結論未超出證據。
  • 經驗、推論與事實區分清楚。
  • 啟發與價值認同，且沒有超出證據。
  • 材料可以公開，必要匿名已完成。
產出：知識基準 B1.0、確認人、確認日期及排除事項。G2 批准必須來自真實人類回覆，頁面展示或按鈕不代表確認。新增實質主張、數據或案例時回到此步；措辭與段落調整可繼續執行。
完成條件：人類明確確認知識基準，核心論點沒有未解決的事實問題。確認失敗退回 04，證據不足則退回 02。


06
AI 規劃
知識圖解（diagram-design）→ 故事主線與視覺規劃
第一步：依 G2 確認的知識稿，用 diagram-design（warm-paper）每章畫一張知識圖解，存 visuals/diagrams/。第二步：以已確認的「啟發與價值」為落點，確定每一章要回答什麼，並標出可能需要視覺解釋的位置。
架構選擇
  • 問題解決型：困境 → 原因 → 方法 → 案例 → 行動。
  • 經驗反思型：事件 → 原先判斷 → 問題 → 新理解 → 適用條件。
  • 主線依「啟發與價值」的建議：切入情境 → 轉折 → 落點；文章的核心句、轉折與結尾須能對應到這一節。
  • AI 可提出兩個簡短架構，依已確認目的選定，說明選擇理由。
  • 每章只有一個主要任務，安排論證、例子與必要轉折。
視覺規劃
  • 先做知識圖解：依 G2 確認的知識稿，用 diagram-design（warm-paper）每章畫一張結構圖，存 visuals/diagrams/，附 README 忠實度說明；不畫未確認內容、不新增事實，PNG 逐張查看。
  • 出圖標準（warm-paper，2026-10-16 定版）：結構按 diagram-design 畫完，一律跑 Skill 內的 scripts/warm-paper/warm-paper-build.py visuals/diagrams/，依序完成：pdm-flat 換皮 → 細線框、杏色起點框、最小字號 16px、去文字底塊、裁掉空白 → 圓形圖示徽章 → 1360px @2x 整頁 PNG → 間距檢查 → 整目錄配色檢查 → 標題長度檢查 → 徽章遺漏檢查 → figure-lint.py 機械檢查。
    ・標題：HTML 的 <h1> 是 PNG 上唯一的標題，短標題 ≤16 字（超過只警告）；萊姆螢光筆 <mark> 可選，只標 1 個真正的關鍵詞，沒有關鍵詞就不標，不按「：」「，」機械標後半句；完整結論寫在說明段。SVG 內的眉標與長標題（class ey／hd）在 PNG 中自動隱藏。
    ・顏色預算：每張只用中性卡片＋青綠連線＋1 個重點色；杏色只在確實要區分「人」時使用；背景不加杏色／萊姆色暈。
    ・色義：杏色＝人／起點／人類決定／限制；青綠＝事實／AI／連線；萊姆＝每張唯一重點（標題 <mark> 與圖內萊姆須指向同一訊息，不同時去掉一處）；中性＝缺口／對照；圖例文字須與顏色一致。
    ・徽章：badges.json 只寫卡片內的錨點文字、lucide 圖示名與色調；腳本實測文字位置，放在卡片內不壓字，卡片太密時退到卡片左上邊緣；同尺寸一組卡片位置統一。放不下時 build 以 exit 1 結束，改用 cx／cy 固定位置或換錨點文字。
    ・擋下出圖（exit 1）：文字重疊、溢出、行距過擠或圖例過近；目錄內仍有 pdm-flat 舊配色；徽章放不下；figure-lint 的 × 項。輸出須依序見到「間隔 OK」「フォルダ全体の配色 OK」且 lint 無 ×，逐張看過 PNG 才算完成。
    ・對齊文章：流程步數、人工關卡次數與術語以文章正文為準。
  • 標記每章對應的 C／E／K 編號，以及可沿用的知識圖解。
  • 標記可能需要視覺解釋的章節及候選位置；這只是候選，最終分鏡依完成的故事文章。
  • 說明型圖的風格與製作規則以 Skill 內 scripts/warm-paper/warm-paper.md 為準；敘事型跟隨 article-figures 的當前版本。
  • PPT 按講述或閱讀情境重組內容，補充講者備註。
產出：知識圖解（每章 HTML＋PNG、badges.json、README：短標題與忠實度說明）；故事主線、章節順序、簡潔大綱、各章依據及候選視覺位置（記錄於 working.md）。
完成條件：各章作用清楚、重要論點有證據安排，視覺可追溯到知識基準。偏離已確認目的回到 03；缺少知識回到 05。


07
AI 生成
先完成故事文章，再依全文配圖
先確保全文論述完整，再改善語言與節奏；文章通讀完成後，才按「配圖分工」製圖：說明型圖用 diagram-design（優先沿用知識圖解並依全文修訂），封面與敘事圖交給 article-figures 分鏡。
第一輪：內容完整
  • 結論優先：標題下先用一小段寫出結論（主要結果、關鍵發現、最大改觀；估算註明口徑），需要時配一張結論圖；後文「結果」章不再重複揭曉。
  • 標題成鏈：先列出全部標題再寫正文；每個標題寫具體訊息，上一個標題留下的問題由下一個回答，只看標題也能讀懂主線；平行小節標出位置，轉折獨立成標題，收尾只留一處「帶得走的」。
  • 以真實情境、具體問題或有依據的觀察切入。
  • 每章圍繞一個主要問題，觀點後接證據、案例或解釋。
  • 段落銜接交代為何接著談下一件事。
  • 結尾回應文章目的，給出具體下一步。
第二輪：表達優化
  • 刪除重複與空泛形容詞，解釋必要術語。
  • 長短句自然交替，段落有疏密與呼吸；短句用於強調、停頓與轉折，長句展開解釋與條件。
  • 節奏跟隨意思與情緒，不機械規定比例，也不把完整意思切成碎句；保留作者聲音。
  • 寫完通讀，檢查拖沓、跳躍、重複句式與突兀停頓；修改後核對原意及必要限制。
  • 核對精簡後是否改變原意或省略限制。
第三輪：依全文配圖
  • 配圖分工：流程、對比、判斷、循環、層級等說明型圖讀取 skills/article-writing-workflow/vendor/diagram-design/SKILL.md（profile warm-paper），優先沿用知識圖解；封面、開場、收尾等敘事圖讀取 skills/article-figures/SKILL.md。兩者皆為用戶指定的外部 Skill 例外，每圖在交接表註明所用 Skill。
  • 輸入：最新全文、版本、需解釋的章節、預計插入位置、數量及明確風格要求；記錄每圖對應章節、原文句子和主要訊息。
  • 按所選 Skill 執行分鏡、模板排版、實際 PNG 渲染、逐圖檢查與優化循環；不得用圖片添加文章沒有的結論。
  • 可視化標準：用形狀表達結構，不做並排文字卡片（一次 vs 重複→分支多行；瓶頸／時間→按比例條形；以前 vs 現在→同尺度對比條；交給誰→判斷流程；誤解 vs 實際→成對行）；一圖一訊息；條長按數值畫，與標題數字不一致時在圖上註明。
  • 抽象內容擬物化：原則、分工、角色等抽象內容不畫成文字層疊，改用日常實物比喻成場景（人的經驗→筆記本、AI 整理→卡片＋放大鏡、人的決定→印章、規則→尺規、成品→文章紙張），實物按真實流程順序擺放、不壓字。
  • 配圖密度：約每 10 個顯示行一張（中文約 40 字／行、日文約 44 字／行），連續 10 行以上無圖須補；每張表達該段一個具體訊息，不為湊數重複。中日兩版分別計算。
  • 最小字號與間距：圖內文字 ≥16px（文章中約縮為 0.65 倍），一開始就按 16px 設計卡片寬與行距；warm-paper-build.py 遇文字重疊、溢出或圖例過近即 exit 1，須改文案或加寬後重跑到「間隔 OK」，不得以縮字通過。
  • 沿用舊圖先查風格：沿用舊版、他語言版或其他文章的圖前，確認已是 warm-paper；腳本對整個目錄檢查，出現「未変換」即 exit 1。
  • 機械檢查 figure-lint（v2.6 新增）：build 最後自動執行 scripts/warm-paper/figure-lint.py <diagrams 目錄>；不經 build 的圖（如 article-figures 的 frames.html）手動執行同一命令。× 必須修到 0：中文圖禁用 palt、日文圖不留中文。! 逐條判斷：「焦点が2つかも」＝標題與圖內萊姆指向不同訊息時去掉一處；「本文にない」＝圖中出現文章沒有的數字或內部名稱（專案代號、wiki、檔名）時刪掉或改成文章用詞；「截圖が広い」＝UI 截圖裁到關鍵區並加 ①②③ 編號，圖說逐號對應。
  • 流程實例圖（實物模擬，v2.6 新增）：要說明「材料怎麼經過流程變成成果」時，不畫抽象方框，畫成實物：素材全用真實檔案（source.md 原文、working.md 診斷與作者回答、知識稿實際章節、實際用過的 PNG、文章實際段落），筆記＝橫線記事本＋手寫體、診斷＝對話視窗、知識稿＝文件頁＋「作者已確認」章、文章＝瀏覽器頁面；用 ①②③ 標同一個問題在每一步的樣子。這類圖不跑 warm-paper-build，須逐張看 PNG 檢查溢出與空白。
  • 提供全部圖中文字的校對清單，區分原文、新寫及縮短。
  • 圖片與可編輯來源存入 visuals/，圖說嵌回 article.md，再以 md2html.py 生成 article.html（標題下自動放可點擊目錄，並列出超過 10 行的無圖段落，交付前須清零），不手改 HTML；檢查縮到文章寬度後的可讀性。
PPT 與限制
  • PPT 直接用可用文件工具生成真實 PPTX／PDF，不以逐頁文字代替檔案。
  • 「情境插畫」（寫實或插畫風）尚未實現：article-figures 不支援，選到時明確說明並建議改用流程、概念或比較圖，不得以其他工具悄悄代做。
  • 指定 Skill 不存在或不可讀取時明確報告，不以同名副本或內建規則冒充；仍可完成不依賴配圖的工作。
  • 寫出文章後，在 working.md 建立「引用對照」：每個 C／E／K 編號被哪些段落、圖號、PPT 頁引用及涉及的數字。
故事化的界線
不得補造對話、心理活動、事件細節、客戶成果或數據。假設情境須明確標示；新增實質內容回到 05 確認。
產出：完整文章 A0.1；文章通讀後的視覺 V0.1（PNG、可編輯來源、校對清單）；working.md 引用對照；尚待處理事項。出圖後交由獨立審圖 Agent 審核（見 08）。
完成條件：全文與所選視覺完整，視覺依最新全文分鏡，沒有未標示的新增事實，所有圖文數據一致。


08
獨立審圖 ＋ AI 自查 ＋ 人類審核 · G3
品質審核與定稿批准
先由不參與製作的獨立審圖 Agent 直接看圖並修正其問題，AI 再自查，最後把需要人類判斷的問題集中提交。
AI 審核
  • 獨立審圖（先做）：派發 Skill 自帶的 agents/figure-reviewer.md，只給文章、PNG 清單與報告路徑，不給製作過程與自評；它先跑 figure-lint，再逐張直接讀圖，以設計大賽得獎選手標準給出分級問題（R 編號）與具體改法，只審不改。阻擋與必修修完後重審，最多三輪；第二輪起只交「本輪改過的圖」清單，逐條核對上一輪 R 項。中日兩版分別審；翻譯版的圖不重畫，沿用原文版 HTML 結構只換文字，審核時附原文版 diagrams 目錄做結構對照（lint 加 --source）。報告中「改正文就能解決」的項目另列，由作者決定改圖或改文。
  • 依原始來源核對事實、引用、數據與案例。
  • 檢查邏輯、完整性、可讀性、故事節奏及作者聲音。
  • 核對圖片／PPT 的文字、標籤、數據與結論。
  • 檢查連結、圖說、版面及交付檔案。
  • 每輪記錄「問題 → 修改 → 驗證結果」；問題以 Q01、Q02 編號記在 working.md。
  • 通讀檢查語言節奏：拖沓、跳躍、重複句式、突兀停頓。
人類審核
  • 準確代表自己的觀點。
  • 重要案例真實，公開範圍合適。
  • 故事表達沒有誇大結果。
  • 願意以自己的名義發布。
  • 明確選擇批准定稿或退回指定問題。
產出：審圖報告（visuals/review/figure-review-<日期>.md，每輪一份）、審核紀錄、修訂版文章與視覺、最終批准紀錄。詳細退回規則見下方品質矩陣與「獨立審圖」。
完成條件：阻擋問題與必修問題全部解決，人類明確批准。連續兩輪卡在同一問題時重查知識或架構，避免反覆只改措辭。

交付成品，也保存下一篇文章可以直接使用的知識與案例。

  • 定稿文章、圖片／PPT 及可編輯來源。
  • 核心知識摘要、主張與證據清單（knowledge-notes.md）。
  • 可重用知識卡、案例卡及來源索引。

  • 交付與發布分開記錄；需代發布時另有渠道、時間及批准紀錄。

選
選配 · 定稿後
日文翻譯與 yomiyasu 潤色
僅在 G3 批准定稿後、且用戶要求日文時執行。不是第十階段，不改變九階段與三個決策點。
步驟
  1. 確認來源版本：以 G3 批准的 article.md 為唯一來源，版本記入 working.md。
  2. 翻譯：存為 article.ja.draft.md；事實、數字、條件、否定與立場一致，預設である常體。
  3. yomiyasu 潤色：讀取 skills/article-writing-workflow/vendor/yomiyasu/SKILL.md 及其 references，存為 article.ja.md。
  4. yomiyasu 檢查：執行 yomiyasu_lint.py 與 yomiyasu_diff.py，候選只修正一次。
  5. 對照中文定稿：逐段確認沒有漏譯、錯譯、增刪事實。
  6. 配圖文字：預設保持原語言；要求日文配圖時另行渲染到 visuals/ja/。
  7. 記錄與交付：記錄領域判斷、lint 分數、採納／未採納候選，交付 article.ja.md。
邊界
  • 定稿未批准時先說明需要 G3，不翻譯未定稿內容。
  • 發現中文定稿本身有事實或邏輯問題時，不在日文版單獨修正；先報告並退回對應階段，重新 G3 後再翻譯。
  • 只調整日文措辭不需要重新 G3。
  • yomiyasu 不存在或腳本無法執行時明確報告，不寫成已完成腳本檢查。

修改連動（依 working.md 引用對照）
  1. 任一 C／E／K 編號的內容或數字改變時，先查引用對照，列出受影響的段落、圖、圖說、替代文字、講者備註及日文版。
  2. 每個受影響位置開一個 Q 項，狀態設為「待驗證」，註明來源編號。
  3. 數字改變時，正文、圖表、圖說、替代文字、講者備註逐一核對，不只改一處。
  4. 全部驗證後關閉 Q 項，更新引用對照與版本記錄；實質主張改變仍按 G2／G3 重新確認。
引用對照只記錄實際引用，不預先填寫。
修改連動檢查（v2.6 新增）：
  1. 改標題後逐章核對標題與正文是否相符；標題是問句時，章首第一句先回答；承接舊標題的過渡語一起改。
  2. 刪段落時，一併檢查只為該段服務的圖與圖說，問作者是否同刪；刪圖或插圖後，正文、圖說、alt 的圖號與目錄 #sec- 錨點連續重排。
  3. article.md 與 article.html 同步修改；有日文版時同一輪同步修改日文版的 md 與 html，不等作者提醒。
  4. 日文版修改後跑 yomiyasu lint 與 diff；自己新增句子引起的新警告必須修掉，分數不得低於修改前。
獨立審圖（v2.5 新增，v2.6 更新）
製作者自己看圖容易放過問題。所有配圖渲染後，派發不參與製作的審圖 Agent，以 Red Dot、D&AD、ADC、Tokyo TDC、Good Design Award 得獎選手的眼光逐張直接讀 PNG，按七個面向審核：一眼訊息、結構表達、視覺層級、字體排版、留白網格、色彩系統、圖文一致，再做全組審視。
  • 阻擋：圖文矛盾、錯字、數字錯誤、文字缺失或溢出、顏色意義用錯。
  • 必修：訊息不清、層級混亂、文章寬度下看不清、未對齊、多焦點。
  • 可選：從「合格」到「得獎」的提升。
  • 先機械、後人眼：審圖前先跑 figure-lint，× 項直接列入報告，! 項看圖後判斷是否成立；lint 通過不代表圖沒問題。
  • 翻譯版對照：兩版並排核對流程步數、關卡次數、節點與分支，翻譯版少步驟或多內容列為阻擋。
  • 複審只看改過的圖：逐條標上一輪 R 項為已解決／部分解決／未解決，未改的圖不重寫結論。
報告的 R 編號轉成 working.md 的 Q 項處理。獨立審圖不是決策點，分數不代表 G3 批准。

07 / RESPONSIBILITIES
由人類決策，AI 完成分析與製作
由專用 Agent article-knowledge-editor 按九階段執行。寫作、查證、審核與整理的方法已內建在專用 Skill；說明型配圖與知識圖解使用 diagram-design、敘事配圖使用 article-figures、日文潤色使用 yomiyasu，是三個用戶指定的例外。
分工責任需要確認的節點
人類提供原始內容、評論、補充經驗、確認事實與觀點、決定保留或刪除、批准定稿03 方向決策；05 知識基準確認；08 最終審核
AI Agent分析診斷、依評論優化、故事與視覺規劃、生成文章與圖片／PPT、自查、修訂及知識整理提交具體成果與待確認事項，依人類決定繼續
每篇文章的執行安排
  1. 材料與診斷：套用任務設定，整理材料，提交診斷及需要人類決定的問題。
  2. 評論與知識確認：依回覆修改，核定事實、觀點、案例及證據。
  3. 架構與生成：以啟發與價值為落點規劃主線，先寫完故事文章，再依全文配圖。
  4. 審核與交付：完成修訂、取得定稿批准，保存文章、視覺、摘要、案例和版本。
時間依材料完整度、篇幅及修改量安排。原始內容可零散提供；重要資訊缺口集中提出，設定未填則使用預設值。
完成判定
  • 文章回應已確認的目的，事實和論證可靠，目標讀者容易理解。
  • 故事表達沒有編造細節或誇大結果。
  • 所選圖片／PPT 與文章一致，檔案可正常開啟。
  • 人類已批准定稿，必要來源、修改紀錄及待確認事項完整。
  • 核心知識摘要和可重用案例已保存，能找到對應的原始依據。
