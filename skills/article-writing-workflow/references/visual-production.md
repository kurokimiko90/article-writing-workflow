# 视觉制作细则

本文件由 SKILL.md 按第 06／07 阶段加载。下文所有 `<skill>` 及脚本相对路径仍以 Skill 根目录为基准；“工作状态与审核记录”见主 Skill 同名小节。

### 知识图解（G2 后，第 06 阶段开头）

把已确认的基础知识稿逐章转成结构图，让作者和读者先“看懂知识”，也作为文章说明型配图的底稿。交付形式含配图时默认执行；“仅文章”或用户说不要时跳过。

1. **时点**：G2 确认后才制作，依据对应的 B 版本。关键事实仍未解决时，不开始依赖这些事实的图；已确认稿保留的非关键未知可在图中明确标注“待作者确认”，不得画成确定事实。
2. **工具**：读取 `<skill>/vendor/diagram-design/SKILL.md` 当前版本、所选 `references/type-*.md` 与 `references/export.md`；默认样式用 `~/.diagram-design/profiles/warm-paper.md`（正本在本 Skill 的 `scripts/warm-paper/warm-paper.md`），用户明确指定其他风格时按对应规则执行。不修改参考 Skill 与 profile。
   - 制作前一次确认实际 Python 运行时；现有脚本使用 Python 3.10+ 语法。下文 python3 均指兼容的解释器，不能默认系统自带版本可用；版本不足时优先选已安装或应用提供的运行时，并记录实际路径与版本。工具未成功启动不得记为检查完成；不为此自动安装新依赖。
3. **范围**：每章一张；内容超出复杂度上限（≤9 节点）时最多拆两张。“来源与待确认事项”“确认记录”等元信息章节不画。每章选最合适的图型（流程、对比、循环、树、层级、泳道、文氏等），避免全篇同一种图；用形状表达结构、不做并排文字卡片；原则、分工、角色等抽象内容图示化、拟物化（日常实物比喻成场景），细则见 `references/methods.md`“可视化标准”。
4. **内容边界**：只用知识稿里的事实；不新增数字、步骤、因果或结论。知识稿标注的口径、AI 推论、作者主观感受、未实现能力等限制要留在图上。归纳的分组名、命名、推定的连线须在 README 的忠实度说明中逐条列出。公开范围同知识稿。
5. **语言与标题**：图内文字跟随知识稿语言，`lang` 对应设定；中文须加 CJK 字体回退（PingFang SC／Hiragino Sans GB／Noto Sans SC）。HTML 的 `<h1>` 是 PNG 上唯一的标题：**短标题 ≤16 字**（全角计），`<mark>` 莱姆荧光笔可选：只标 1 个真正的关键词，不按“：”“，”机械标后半句；没有关键词就不标（2026-10-22 用户指正：高亮出现在莫名其妙的地方）；完整结论写在说明段（deck），不塞进标题。SVG 内若有眉标／长标题，用 class `ey`／`hd`，导出 PNG 时自动隐藏。重点色（莱姆）每张只给 1 个焦点。
6. **出图标准（结构按 warm-paper 画；对外配图默认再换 swiss-red 皮肤，2026-10-30 用户选定 C 方案）**：warm-paper 出图并通过检查后，跑 `python3 <skill>/scripts/warm-paper/swiss-red-skin.py visuals/diagrams visuals/diagrams-C --article article.md`，文章引用 `diagrams-C/`。焦点、标题和手机字号规则见 `scripts/warm-paper/swiss-red.md`。采用 warm-paper 时，结构按 diagram-design 画完后跑 `python3 <skill>/scripts/warm-paper/warm-paper-build.py visuals/diagrams/`，它依序完成：pdm-flat 配色换皮 → 细线框／杏色起点框／最小字号 16px／去文字底块／裁掉空白 → 圆形图标徽章 → 1360px @2x 整页 PNG → 间距检查 → 标题长度检查。用户明确采用其他风格时按 methods.md 对应规则渲染并检查，不用默认换皮覆盖已选风格；字号、间距、忠实度与独立审核要求仍适用。脚本、profile 与图标都随本 Skill 放在 `scripts/warm-paper/`（`warm-paper.md` 是 diagram-design 的 warm-paper profile 正本，`~/.diagram-design/profiles/` 下的同名文件只是指向这里的 symlink；换机器时重建该 symlink 即可）。规则细节见 `scripts/warm-paper/warm-paper.md`，以下配色条款适用于 warm-paper：
   - **颜色预算（2026-10-22 用户指正“颜色超多”）：** 每张图只用中性卡片＋青绿连线＋1 个重点色；杏色只在确实要区分“人”时使用。背景不加杏色／莱姆色晕（沿用旧图当模板时删掉 `body::before` 的 radial-gradient）。
   - 色义：杏色＝人／起点／人类决定／限制；青绿＝事实／AI／连线；莱姆＝唯一重点；中性＝缺口／对照。图例文字须与颜色一致（写“绿色”“杏色框”，不写“蓝色”“灰框”）。
   - 徽章：在 `visuals/diagrams/badges.json` 只写 `{"anchor":"卡片内的一段文字","icon":"lucide 名","tone":"apricot|teal|lime|neutral|ink"}`，位置由脚本实测自动放在卡片内、不压字（卡片内没空位时退到卡片左上边缘）；同尺寸的一组卡片位置统一，组内任一张放不下则整组不加（脚本会警告）。只给关键节点加，不为装饰硬塞。
   - **沿用旧图先查风格（2026-10-20 事故：日文版 01–03 为 pdm-flat 旧图，只对新图跑脚本而漏掉）：** 采用 warm-paper 时，沿用既有图先确认已是 warm-paper；脚本会检查整个 diagrams 目录，出现“× warm-paper 未変換”即 exit 1，必须转换并检查图例颜色词与标题长度，交付前确认“フォルダ全体の配色 OK”。用户明确采用其他风格时按已选风格核对，不将其判为待转换旧图。任何全目录构建改变了已有 PNG 或图源后，按实际变化更新审核范围，不能仍记为原样复用。
   - **最小字号与间距（2026-10-21 事故：图宽 1280 在文章里只显示约 880px，12–13px 字实际只剩 8–9px 看不清；字号统一放大后又大量出现文字溢出框、行距挤、图例压色块）：** 图内任何文字 ≥16px（脚本强制把更小的字号提到 16，不能靠缩字解决排版）。因此一开始就按 16px 设计：卡片宽 ≥ 最长一行字数×17＋32；同一张卡片上下行距 ≥1.4×字号；文案先求短（副标题 ≤8 字为宜），日文版比中文长约 3 成，译完要重新量。脚本会自动把堆叠行拉开到 1.4 倍、按文字宽重排胶囊行与图例；仍有“文字重叠／近すぎ／枠からはみ出し／凡例の色と近すぎ”时，build 以 exit 1 结束（“未完成扱い”）——必须改文案（缩短、拆行）或加宽框后重跑，直到输出“間隔 OK”。不要为通过检查而删除警告或调小字号。
   - 执行前先跑 `scripts/self_check.py` 与 `verify-geometry.py`（存在时）；执行后逐张打开 PNG，确认无缺字、溢出、徽章压线、图例与颜色不符。没看过的图不写为已检查。
   - **机械检查 figure-lint（2026-10-26 四篇审图后加入）：** build 最后会自动跑 `scripts/warm-paper/figure-lint.py <diagrams_dir>`；独立审核须显式传入 `--article <对应的 knowledge-base.md 或 article.md>`。用 article-figures 等不经 build 的图（如 frames.html）也要检查。× 必须修到 0；! 逐条判断：“焦点が2つかも”＝标题高亮与图内莱姆指向不同讯息时去掉一处；“本文にない”＝图里出现参照正文没有的数字或内部名称时核对、删除或改成对应正文用词；“截圖が広い”＝UI 截图裁到关键区并加编号标签，图注逐号对应。中文图禁用 palt、日文图不留未说明的中文残留、徽章不能压字。
   - **对齐对应正文的用词与数量：** 第 06 阶段以已确认的 knowledge-base.md 为准，第 07 阶段文章配图以 article.md 为准；记录具体版本。流程步数、人工关卡次数、术语及限定须一致，例如对应正文写“审查 2 次”，图里就要有 2 个审查节点。尚未确认的事项不能画成已核实事实。
7. **检查、审图与交付**：保存到 `visuals/diagrams/NN-<英文短名>.html／.png`、`badges.json` 与 `README.md`（文件｜图型｜章节｜回答的问题＋短标题＋忠实度说明）。build 后额外运行 `python3 <skill>/scripts/warm-paper/figure-lint.py visuals/diagrams/ --article knowledge-base.md`，避免以尚未完成或旧版文章作依据；检查后逐张看 PNG，再按“配图独立审核”以已确认知识稿为参照独立审图，阻挡与必修项修正并验证解决，可选项记录取舍。
   - 图按对应章节嵌回 knowledge-base.md，附图说、替代文字和图档相对路径；同步生成 knowledge-base.html，HTML 内嵌图片数据以保持单文件离线可读，原 PNG 与可编辑来源仍保留。打开 HTML 核对图片、章节、手机显示及打印排版，不能只交独立图档。图说不得增加知识稿没有的主张。
   - 在 working.md 记录 B 版本、图档及来源内容的 SHA-256、审图报告、未解决项与引用对照；没有关键事实变化时，嵌图和排版沿用原 G2，不新增人类确认点。B 版变化后按引用对照将受影响图标为“待验证”，修订、复审并同步知识稿两种格式。
8. **不是决策点**：知识图解不增加人类关卡，也不代表 G3；作者可随时就图提出修改。

### 配图分工（第 07 阶段）

| 图的作用 | 使用 Skill | 说明 |
|---|---|---|
| 说明结构：流程、步骤、对比、判断分支、循环、层级、职责分工、适用范围 | diagram-design（warm-paper，出图跑 warm-paper-build） | 优先沿用已审知识图解；原样沿用只核对文章语境，改图则另存到 visuals/article/，按变化复审，保留知识稿原图；交接表记录来源图号及报告 |
| 叙事与氛围：封面、开场、收尾、金句卡等非结构图 | article-figures（当前默认 warm-paper） | 按全文分镜，流程同原规定 |

同一篇文章可两者并用；每张图在交接表注明所用 Skill。用户指定单一 Skill 或风格时优先。

### 配图输入与交付

将最新故事文章全文、版本、需要解释的章节、预计插入位置、数量及明确风格要求作为 article-figures 的输入。记录每图对应章节、原文句子和主要讯息。不得用图片添加文章没有的结论。

按指定Skill执行分镜、模板排版、实际PNG渲染、逐图检查和优化循环，提供全部图中文字的校对清单，区分原文、新写及缩短。中文文章使用中文校对清单。默认采用该Skill当前默认风格；用户另行指定风格或数量时优先。

“情境插画”（写实或插画风格）尚未实现：article-figures 不支持此类图。用户选择时明确说明未支持，建议改用流程、概念或比较图，或交回用户决定；不得以其他工具悄悄代做。

实际图片和可编辑来源保存到本篇文章的 `visuals/`（知识图解在 `visuals/diagrams/`），将图说与图片嵌回 article.md／article.html，并检查缩到文章显示宽度后的可读性。文章实质内容变更时重核对应分镜和图面。指定Skill（diagram-design 或 article-figures）不存在或不可读取时明确报告，不以项目同名副本或内置制图规则冒充已使用它；仍可完成不依赖配图的工作。

### 流程实例图（实物模拟）

要说明“材料怎么经过流程变成成果”时（2026-10-22 用户指正：抽象方框流程图“不好，我要实际记事本的样子，图片，文章的样子”），画成实物模拟，不画抽象方框：

1. **素材全用真实文件**：原始笔记取 `source.md` 原文；AI 诊断取 `working.md` 诊断表的真实 D 项与作者回答（M02 等）；知识稿显示 `knowledge-base.md` 实际的全部章节结构，只展开问题落进去的章节和条目（含来源标注）；图片直接嵌入实际用过的 PNG；文章用实际标题与段落。不编造，客户与系统名照公开范围匿名。
2. **外观像实物**：笔记＝横线记事本＋手写体（LXGW WenKai），AI 指出处画红色波浪线；诊断＝对话视窗（AI 指出／作者回答交替）；知识稿＝文件页＋“作者已确认”章；图片＝原图缩略；文章＝浏览器页面。
3. **一条线索贯穿**：用 ①②③ 标同一个问题在每一步的样子，图脚注明出处。
4. **制作**：HTML 绝对定位排版，Chrome headless `--force-device-scale-factor=2` 截图；正文字 ≥16px，颜色只用纸色、墨色、红（AI 指出）、青绿（箭头与作者）。不跑 warm-paper-build，因此必须逐张看 PNG 检查溢出与空白。范例：`exports/articles/article-writing-workflow-story/visuals/diagrams/33-note-journey-real.html`。
