# 文章撰写与知识沉淀

> **路径约定：** 本文中 `<skill>` 指本 Skill 目录（即本 SKILL.md 所在目录）。`scripts/`、`references/`、`agents/`、`vendor/` 等相对路径都以它为基准；`<skill>/../article-figures/` 是同一仓库中的封面与叙事图 Skill；`vendor/` 下是第三方 Skill 副本（来源见 `vendor/SOURCES.md`）。

这是独立的专用 Skill。按用户确认的九阶段流程完成文章及所选视觉交付，由专用 Agent `article-knowledge-editor` 执行，或由当前 AI 直接执行本 Skill。人类掌握内容方向、事实确认及最终决策。

本 Skill 已将参考材料中相关的写作、查证和知识整理方法提取为内部规则。视觉制作是用户指定的例外，按用途分工使用两个制图 Skill：
- **结构图解**（流程、结构、对比、判断、循环、层级等说明型图）：读取并使用 `<skill>/vendor/diagram-design/SKILL.md`，套用 profile `~/.diagram-design/profiles/warm-paper.md`。用于 G2 后的“知识图解”与第 07 阶段的说明型配图（见“知识图解”与“配图分工”）。
- **叙事配图**（封面、开场、氛围、收尾等非结构图）：读取并使用 `<skill>/../article-figures/SKILL.md`，根据已完成的故事文章制作。

定稿后的日文翻译是另一个用户指定例外：译成日文后，必须读取并使用 `<skill>/vendor/yomiyasu/SKILL.md` 润色日文（见“定稿后日文翻译”）。

配图独立审核是本 Skill 自带的独立 Agent：出图后必须派发 `agents/figure-reviewer.md`（本 Skill 目录内，正本），由它直接读取 PNG、以设计大赛得奖选手标准审核（见“配图独立审核”）。其余环节不加载或调用其他 Agent／Skill。

## 开始与默认设置

1. 接收原始材料，保留原文。未提供材料时，只整理已有任务设置，再请用户提供材料；不要生成虚构诊断或文章。
2. 读取 [任务选项与默认值](references/defaults.md)。优先级：用户最新明确指示 → 材料中明确的任务说明 → 默认值。空白、未选择或空白自定义值使用默认值，不逐项追问。
3. 提交简短任务摘要，标明用户指定、材料明确说明或默认。不为默认设置增加确认关卡；直接开始诊断。
4. 只追问影响方向、关键事实或公开范围的问题。用户明确要求优先于通用 Skill 建议。

## 九阶段

| 阶段 | 执行内容 | 产出与完成条件 |
|---|---|---|
| 01 输入 | 整理任务设置、原始材料及来源 | 可辨识主题的素材包、任务摘要、关键缺口 |
| 02 诊断 | 检查事实、逻辑、概念、理解障碍及内容价值；区分事实、经验、推论、未知 | 简洁诊断表、问题及具体改法；必要查证依任务设置进行 |
| 03 人类评论与决策 | 集中提交方向、关键问题与素材取舍；接受保留、修正、深化、删除、待确认 | **G1：人类明确决定方向**，记录评论与补充材料 |
| 04 依评论优化 | 整合补充，修正知识结构、证据及表述，逐项处理评论；提炼“启发与价值” | HTML基础知识稿（含启发与价值）、修改摘要、待确认事项 |
| 05 人类确认基础知识 | 提交完整HTML知识稿，包含目的、事实、核心观点、启发与价值、案例、证据、适用条件及公开范围 | **G2：人类确认知识基准**，保存对应版本；关键事实无未解决问题 |
| 06 故事与视觉规划 | 先按已确认知识稿逐章制作“知识图解”（diagram-design）；再以已确认的“启发与价值”为落点建立故事主线、论证顺序，标记需要视觉解释的章节及可沿用的知识图解 | 知识图解 `visuals/diagrams/`（每章一张、PNG＋HTML＋README）；简洁大纲、各章依据、候选视觉位置；最终配图依据完成的故事文章 |
| 07 生成 | 先完成故事文章并检查事实与语言节奏，再按“配图分工”制作：说明型图用 diagram-design（可沿用并按全文修订知识图解），封面与叙事图用 article-figures；PPT按所选格式生成 | 完整文章、真实视觉文件、图说／必要备注明确，图文一致 |
| 08 品质审核 | 先收回独立审图报告并修正阻挡／必修项；AI 再核对来源、逻辑、可读性、故事节奏、完整性与视觉，先修正再提交人类 | **G3：人类批准定稿**；阻挡及必修问题已解决 |
| 09 交付与沉淀 | 保存定稿、所选视觉、摘要、可重用案例、来源及版本记录 | 实际文件可打开，知识可独立理解且可追溯 |

默认按顺序推进。已经确认且未改变的事项沿用，不要求重复确认。人类新消息是当前流程的反馈，除非明确更换任务。

## 三个人类决策点

- 在 G1、G2、G3 提交具体成果及需要决定的事项；记录决定对应的版本或文件。
- 空白、时间经过、沉默、默认值以及一般性的“继续做”不等于对未展示成果的批准。用户已明确认可所展示成果，则沿用该授权，不重复询问。
- 等待决策时结束当前轮次，说明下一步并保留待确认事项；可整理已确认材料，不生成依赖未确认内容的成果。
- G2 后新增或改变实质主张、数据、案例结果或适用范围，更新基准并重新确认；纯措辞、段落和排版调整无需重复 G2。
- 定稿后的实质内容修改或重要视觉结论变化需再次 G3；批准始终对应实际成果版本。

## 启发与价值

第 04 阶段起，基础知识稿必须有“启发与价值”一节，按 [本 Skill 的执行方法](references/methods.md) 的“启发提炼”产出，并随知识稿在 G2 确认。它回答“读者为什么值得读、读完能带走什么”，是第 06 阶段故事主线与结尾的依据。

- 每条启发标明依据的 C／E／K 编号，区分作者原话与 AI 推论；不能超出证据。
- 必含：一句话核心启发、新理解（常见认知与本案差异）、可迁移做法、适用前提与代价、建议故事主线。
- G2 后文章的核心句、转折与结尾建议须能对应到这一节；文章写出新的启发时，回写知识稿并按 G2 规则处理实质变化。

## 内容与审核边界

- 不补造事实、对话、心理活动、案例过程、成果或数据。假设示例明确标注，不当作真实案例保存。
- 主张不能超出证据；作者观察和推论保留身份及适用条件。关键内容无法查证时删除、缩小表述或交回人类决定。
- 不以故事性掩盖证据缺口；不强制人物弧线、英雄旅程、第一人称或书籍结构。
- 重要主张、证据和案例可用 C／E／K 编号关联；小文章也可用章节与来源链接，只需保持可追溯。
- 问题分为阻挡、必修、可选，以 Q01、Q02 编号记录在 working.md；状态按“新发现 → 修改中 → 待验证 → 已解决”推进，没有验证结果不得标为已解决。不采用的建议保留理由。
- 按下表九个面向判断退回阶段：

| 面向 | 通过标准 | 退回阶段 |
|---|---|---|
| 事实 | 关键主张有依据，来源与情境正确，未知已标示 | 02 查证／05 确认 |
| 逻辑 | 前提、证据与结论一致，反例与限制清楚 | 04 知识稿／06 架构 |
| 完整性 | 回答文章的主要问题，步骤可理解 | 06 架构／07 初稿 |
| 可读性 | 目标读者能理解概念、例子及操作 | 07 初稿 |
| 故事节奏 | 结论在标题下先给出；标题串成问答链，只看标题能读懂主线；各章提供新内容并推进，不重复揭晓 | 06 架构／07 初稿 |
| 语言韵律 | 长短、疏密与停顿自然，无机械交替或刻意碎句，原意与条件完整 | 07 语言修订 |
| 作者声音 | 符合作者立场与已指定的表达方式 | 07 初稿 |
| 视觉一致性 | 图文数据、标签、用词与结论一致 | 07 配图（依最新全文重新分镜） |
| 交付品质 | 文件、链接、字体、图说及排版正常 | 07 制作／09 交付 |

- **修改连动：** 第 07 阶段写出文章后，在 working.md 建立“引用对照”，记录每个 C／E／K 编号被哪些章节段落、图号、PPT 页引用，以及涉及的数字。之后知识基准、文章或视觉中任一编号的内容或数字改变时：
  1. 先查引用对照，列出所有受影响的段落、图、图说、替代文字、讲者备注及日文版。
  2. 每个受影响位置在审核表开一个 Q 项，状态设为“待验证”，注明来源编号。
  3. 数字改变时，正文、图表、图说、替代文字、讲者备注逐一核对，不只改一处。
  4. 全部验证后关闭 Q 项，更新引用对照与版本记录；实质主张改变仍按 G2／G3 规则重新确认。
  引用对照只记录实际引用，不预先填写。
- **修改连动检查（2026-10-22 用户指正）：**
  1. 改标题后逐章核对标题与正文是否相符，不只换字；标题是问句时，章首第一句先回答；章名改掉后，承接旧标题的过渡语（如“补上：”）一起改。
  2. 删段落时，一并检查只为该段服务的图与图说，问作者是否同删；删图或插图后，正文、图说、alt 的图号连续重排，目录 `#sec-` 锚点同步重排。
  3. article.md 与 article.html 同步修改；有日文版时同一轮同步修改日文版的 md 与 html，不等作者提醒。
  4. 日文版修改后跑 yomiyasu lint 与 diff；自己新增的句子引起的新警告必须修掉，分数不得低于修改前。
- 每轮记录问题、修改及验证结果。两轮仍卡在同一问题时检查材料或结构原因；自评分数不代表事实核对或人类批准。

## 专用执行方法

诊断和写作时读取 [本 Skill 的执行方法](references/methods.md) 中相关部分。配图部分定义如何将故事文章交给用户指定的 article-figures Skill；制图规范读取其当前文件，避免复制旧版本。PPT和知识保存仍按本 Skill 内部方法执行。

- 每章一个主要任务，以具体问题或有依据的实例开场，用证据支撑观点。
- 句子与段落有自然的长短、疏密和停顿变化；按内部方法的“语言节奏与韵律”写作，并在第 08 阶段通读检查，不机械规定长短比例。
- 有真实参考文章时提取句长、语气、术语和转场偏好，否则使用默认语气。
- 关键证据不足且允许查证时直接用搜索、网页读取工具核对，保存来源与不确定性。
- 文章配图按“配图分工”选用 diagram-design 或 article-figures；先完整写好故事文章，再按全文的主线、章节及实际句子分镜，不能只根据基础知识稿生成（知识图解是知识稿的图，不等于文章配图，沿用时须按全文核对）。数量遵循任务设置，默认约每 10 个显示行一张、连续 10 行以上无图须补（细则见 `references/methods.md`“配图密度”）；风格和制作规范遵循指定Skill的当前版本。
- PPT 直接用可用文件生成工具制作真实 PPTX／PDF，不将逐页文字当作文件交付。
- 知识直接保存为本地 Markdown，附来源、条件、限制和确认状态；需要时在用户指定资料中去重。

不派发给通用写作、研究、视觉或知识管理角色。除用户另有指示，专用 Agent 自行完成流程。不添加营销、SEO、Bot、自动排程、跨存储同步或系统开发工作，不修改参考 Skill 与全局角色。

### 知识图解（G2 后，第 06 阶段开头）

把已确认的基础知识稿逐章转成结构图，让作者和读者先“看懂知识”，也作为文章说明型配图的底稿。交付形式含配图时默认执行；“仅文章”或用户说不要时跳过。

1. **时点**：G2 确认后才制作，依据对应的 B 版本；不画未确认内容。已确认稿中仍标“待确认”的章节可画，但图内标注“待作者确认”。
2. **工具**：读取 `<skill>/vendor/diagram-design/SKILL.md` 当前版本、所选 `references/type-*.md` 与 `references/export.md`；样式用 `~/.diagram-design/profiles/warm-paper.md`（正本在本 Skill 的 `scripts/warm-paper/warm-paper.md`）。不修改 Skill 与 profile。
3. **范围**：每章一张；内容超出复杂度上限（≤9 节点）时最多拆两张。“来源与待确认事项”“确认记录”等元信息章节不画。每章选最合适的图型（流程、对比、循环、树、层级、泳道、文氏等），避免全篇同一种图；用形状表达结构、不做并排文字卡片；原则、分工、角色等抽象内容图示化、拟物化（日常实物比喻成场景），细则见 `references/methods.md`“可视化标准”。
4. **内容边界**：只用知识稿里的事实；不新增数字、步骤、因果或结论。知识稿标注的口径、AI 推论、作者主观感受、未实现能力等限制要留在图上。归纳的分组名、命名、推定的连线须在 README 的忠实度说明中逐条列出。公开范围同知识稿。
5. **语言与标题**：图内文字跟随知识稿语言，`lang` 对应设定；中文须加 CJK 字体回退（PingFang SC／Hiragino Sans GB／Noto Sans SC）。HTML 的 `<h1>` 是 PNG 上唯一的标题：**短标题 ≤16 字**（全角计），`<mark>` 莱姆荧光笔可选：只标 1 个真正的关键词，不按“：”“，”机械标后半句；没有关键词就不标（2026-10-22 用户指正：高亮出现在莫名其妙的地方）；完整结论写在说明段（deck），不塞进标题。SVG 内若有眉标／长标题，用 class `ey`／`hd`，导出 PNG 时自动隐藏。重点色（莱姆）每张只给 1 个焦点。
6. **出图标准（warm-paper，2026-10-16 定版）**：结构按 diagram-design 画完后，一律跑 `python3 <skill>/scripts/warm-paper/warm-paper-build.py visuals/diagrams/`，它依序完成：pdm-flat 配色换皮 → 细线框／杏色起点框／最小字号 16px／去文字底块／裁掉空白 → 圆形图标徽章 → 1360px @2x 整页 PNG → 间距检查 → 标题长度检查。脚本、profile 与图标都随本 Skill 放在 `scripts/warm-paper/`（`warm-paper.md` 是 diagram-design 的 warm-paper profile 正本，`~/.diagram-design/profiles/` 下的同名文件只是指向这里的 symlink；换机器时重建该 symlink 即可）。规则细节见 `scripts/warm-paper/warm-paper.md`，要点：
   - **颜色预算（2026-10-22 用户指正“颜色超多”）：** 每张图只用中性卡片＋青绿连线＋1 个重点色；杏色只在确实要区分“人”时使用。背景不加杏色／莱姆色晕（沿用旧图当模板时删掉 `body::before` 的 radial-gradient）。
   - 色义：杏色＝人／起点／人类决定／限制；青绿＝事实／AI／连线；莱姆＝唯一重点；中性＝缺口／对照。图例文字须与颜色一致（写“绿色”“杏色框”，不写“蓝色”“灰框”）。
   - 徽章：在 `visuals/diagrams/badges.json` 只写 `{"anchor":"卡片内的一段文字","icon":"lucide 名","tone":"apricot|teal|lime|neutral|ink"}`，位置由脚本实测自动放在卡片内、不压字（卡片内没空位时退到卡片左上边缘）；同尺寸的一组卡片位置统一，组内任一张放不下则整组不加（脚本会警告）。只给关键节点加，不为装饰硬塞。
   - **沿用旧图先查风格（2026-10-20 事故：日文版 01–03 为 pdm-flat 旧图，只对新图跑脚本而漏掉）：** 沿用既有图（旧版本、其他语言版、其他文章的图）前，先确认它已是 warm-paper；脚本结束时会检查整个 diagrams 目录（含未传入的旧图），出现“× warm-paper 未変換”即 exit 1，必须先转换（不带文件参数重跑即可），再检查图例颜色词（旧 pdm-flat 图常写“蓝/青”，须改成“绿/莱姆”）与标题长度。交付前确认输出末尾是“フォルダ全体の配色 OK”。
   - **最小字号与间距（2026-10-21 事故：图宽 1280 在文章里只显示约 880px，12–13px 字实际只剩 8–9px 看不清；字号统一放大后又大量出现文字溢出框、行距挤、图例压色块）：** 图内任何文字 ≥16px（脚本强制把更小的字号提到 16，不能靠缩字解决排版）。因此一开始就按 16px 设计：卡片宽 ≥ 最长一行字数×17＋32；同一张卡片上下行距 ≥1.4×字号；文案先求短（副标题 ≤8 字为宜），日文版比中文长约 3 成，译完要重新量。脚本会自动把堆叠行拉开到 1.4 倍、按文字宽重排胶囊行与图例；仍有“文字重叠／近すぎ／枠からはみ出し／凡例の色と近すぎ”时，build 以 exit 1 结束（“未完成扱い”）——必须改文案（缩短、拆行）或加宽框后重跑，直到输出“間隔 OK”。不要为通过检查而删除警告或调小字号。
   - 执行前先跑 `scripts/self_check.py` 与 `verify-geometry.py`（存在时）；执行后逐张打开 PNG，确认无缺字、溢出、徽章压线、图例与颜色不符。没看过的图不写为已检查。
   - **机械检查 figure-lint（2026-10-26 四篇审图后加入）：** build 最后会自动跑 `scripts/warm-paper/figure-lint.py <diagrams_dir>`；用 article-figures 等不经 build 的图（如 `frames.html`）要手动跑同一命令。× 必须修到 0（中文图禁用 `palt`、日文图不留中文、徽章放不下改用 `cx/cy` 固定）；! 逐条判断：“焦点が2つかも”＝标题 `<mark>` 与图内莱姆指向不同讯息时去掉一处；“本文にない”＝图里出现文章没有的数字、内部名称（项目代号、wiki、文件名、内部流程）时删掉或改成文章用词；“截圖が広い”＝UI 截图裁到关键区并加 ①②③ 编号标签，图注逐号对应。
   - **一律对齐文章用词与数量：** 流程步数、人工关卡次数、术语（如“位置合わせ”“ワークベンチ”）以文章正文为准；文章写“审查 2 次”，图里就要有 2 个审查节点。
7. **交付**：保存到 `visuals/diagrams/NN-<英文短名>.html／.png`、`badges.json` 与 `README.md`（文件｜图型｜章节｜回答的问题＋短标题＋忠实度说明）。在 working.md 记录依据的 B 版本及引用对照。知识稿实质变更（B 版升级）时，按引用对照把受影响的图标为“待验证”并重画。
8. **不是决策点**：知识图解不增加人类关卡，也不代表 G3；作者可随时就图提出修改。

### 配图独立审核（第 07 阶段出图后、第 08 阶段前）

制作者自己看图容易放过问题（2026-10-22 用户指定）。所有配图（知识图解沿用图、说明型图、叙事图）渲染完成后，派发本 Skill 自带的独立审图 Agent 审图：

1. **派发方式**：Agent 定义正本是本 Skill 的 `agents/figure-reviewer.md`。用 `install.sh` 安装后，Claude Code 可用 `subagent_type: "article-figure-reviewer"` 派发；该类型不可用时（未安装、Codex 等其他环境），改派一个全新上下文的子 Agent，第一步要求它完整读取 `<skill>/agents/figure-reviewer.md` 并按其执行。不可由制作者在当前上下文自审代替。只交给它：文章目录、`article.md` 路径、语言版本、PNG 清单、报告输出路径（`visuals/review/figure-review-<日期>.md`，日文版用 `visuals/review/figure-review-<日期>.ja.md`）。不附制作过程、自评或“脚本已通过”等说明，保持独立视角。
2. **审核标准**：以 Red Dot／D&AD／ADC／Tokyo TDC／Good Design 得奖选手的眼光，逐张直接读图，按一眼讯息、结构表达、视觉层级、字体排版、留白网格、色彩系统、图文一致七个面向给分级问题与具体改法，并做全组审视。规则以该 Agent 文件为准。
3. **处理结果**：报告中的 R 编号转成 working.md 的 Q 项（阻挡／必修／可选沿用）。阻挡与必修全部修正后重跑 warm-paper-build（或对应 Skill 的渲染），再派发一次审核验证；可选项逐条决定采用或记录不采用理由。最多三轮，第三轮仍有同一阻挡／必修问题时，按“两轮卡住”规则检查文案或结构原因，交回人类决定。
4. **中日两版**分别审核；日文图文字较长，常出现中文版没有的溢出与断行问题。翻译版的图**不重画**：沿用原文版已修好的 HTML 结构，只替换文字（`lang` 改成对应语言），再跑 build；派发审核时把原文版 diagrams 目录一并交给审图 Agent 做结构对照，figure-lint 用 `--source <原文版 diagrams>` 检查菱形与卡片数量（2026-10-26：日文版 05 独立重画后少了第二次审查）。
5. **复审只看改过的图：** 修正后第二轮起，派发时附“本轮改过的图”清单，审图 Agent 只复审这些图并核对上一轮 R 项是否解决，全组审视沿用上一轮结论（除非改动影响全组）。
6. **正文修改另列：** 审图报告中“改正文就能解决”的项目（例：截图是方框而正文写“丸”）单独列出，由作者决定改图还是改文，不在图上硬改。
7. **不是决策点**：独立审图不代表 G3，分数不代表人类批准。G3 提交时附最新审图报告路径与未解决项。

### 定稿后日文翻译（可选）

仅在 G3 批准定稿后、且用户要求翻译成日文时执行；未要求时不翻译，也不预建文件。翻译不是第十阶段，不改变九阶段与三个决策点。

1. **确认来源版本**：以 G3 批准的 article.md 版本为唯一来源，在 working.md 记录版本。定稿尚未批准时，先说明需要 G3，不翻译未定稿内容。
2. **翻译**：译成自然的日文，保存为 `article.ja.draft.md`。事实、数字、单位、条件、限定、否定、案例结果及人称立场与中文定稿一致；不增删主张。专有名词、产品名、Skill 名、命令和路径保持原样。默认使用である常体；文章明显面向读者说明时可用です・ます体，全文统一。标题、图说和 alt 文字一起翻译。
3. **yomiyasu 润色**：读取 `<skill>/vendor/yomiyasu/SKILL.md` 的当前版本，以及其中引用的 `references/gemini-syntax.md`、`references/slop-catalog.md` 和对应领域文件（`references/domains/tech.md`／`business.md`／`essay.md`）。按其 Step 1–4 判断领域，修正不自然的比喩、主述关系、过度装饰和单调文末，保存为 `article.ja.md`。
4. **yomiyasu 检查**：对 `article.ja.md` 运行 `python3 -I <skill>/vendor/yomiyasu/scripts/yomiyasu_lint.py article.ja.md`；再运行 `python3 -I <skill>/vendor/yomiyasu/scripts/yomiyasu_diff.py article.ja.draft.md article.ja.md --stance=<勧め|決まり|説明>`，无法判断立场时省略 `--stance`。逐条判断候选，按 yomiyasu 规则只修正一次，不为消除警告反复改写。
5. **对照中文定稿**：yomiyasu 只比较日文前后差异，看不到中文原文。润色后逐段对照 article.md，确认没有漏译、错译、新增或删除事实，数字与条件一致。
6. **配图文字**：图片内文字默认保持原语言，不自动重做。用户要求日文配图时，用 article-figures 以 `article.ja.md` 为依据另行渲染到 `visuals/ja/`，并附日文校对清单。
7. **记录与交付**：在 working.md 记录来源版本、领域判断、lint 分数、diff 中采纳和未采纳的候选、对照中发现的问题。交付 `article.ja.md`，并说明 yomiyasu 主要修改和需要作者确认的日文表达。

翻译中发现中文定稿本身有事实或逻辑问题时，不在日文版单独修正；先报告，按审核边界退回对应阶段，修订后重新 G3，再翻译。只调整日文措辞时，不需要重新 G3。yomiyasu 不存在或脚本无法运行时明确报告；仍可按其 SKILL.md 规则人工检查，但不得写成已完成脚本检查。

## 编号与版本

- **素材：** 收到的原始材料在 source.md 依来源编 M01、M02，记录名称、来源、日期、摘要和公开限制。
- **知识：** 主张、证据、案例沿用 C／E／K 编号；诊断用 D、审核问题用 Q。
- **知识基准：** 首次 G2 确认为 B1.0；实质主张、数据、案例结果或适用范围改变时升为 B2.0 并重新 G2。
- **文章：** 草稿依 A0.1、A0.2 迭代；G3 批准后为 A1.0。之后纯措辞调整记为 A1.1，实质修改重新 G3 后升 A2.0。
- **视觉：** 第 07 阶段文章通读完成后才开始 V0.1；随文章修订迭代，G3 批准后为 V1.0。每版记录依据的文章版本。
- **知识图解：** 依 G2 版本编 D-B1.0 等（与所依据的知识基准同号）；B 版升级后重画为对应新号。
- **日文版：** 记录译自哪个 A 版；不单独编主版本。
- 每个成果在 working.md 记录所用知识基准版本。版本号只记在 working.md，不混入定稿正文。

## 文件与最终交付

默认在项目 `exports/articles/<文章短名>/` 保存；用户指定位置优先。同名任务先检查既有文件，修订保留旧稿或修改记录。

使用 [工作与交付模板](references/templates.md) 按需保存：

- `source.md`：收到的原始材料与来源。
- `working.md`：设置、诊断、评论、当前阶段、大纲、审核及修改记录。
- `knowledge-base.html`：基础知识稿的主要审阅交付，包含完整事实、观点、证据、案例、版本与确认状态；第04阶段起生成并优先打开／链接HTML。
- `knowledge-base.md`：同一知识稿的可维护文本来源；每次修订同步HTML，不只输出Markdown，也不把摘要当成完整知识稿。
- `article.md`：文章初稿至定稿，必要时保留版本副本。
- `article.html`：供人类阅读的单文件版，由 `python3 <skill>/scripts/md2html.py article.md article.html` 从 article.md 生成（标题下自动放可点击目录，列出全部 ## / ### 标题）；每次改 article.md 后重跑，不手改 HTML。
- `article.ja.draft.md`／`article.ja.md`：仅在定稿后要求日文时创建；前者为直接译稿，后者为 yomiyasu 润色后的日文交付版。
- `knowledge-notes.md`：最终摘要、可重用案例、来源、适用条件与确认状态。
- `visuals/`：仅选配图或 PPT 时创建，保存真实文件、可编辑来源及图说／备注。
- `visuals/diagrams/`：G2 后的知识图解（每章 HTML＋PNG）及 `README.md`。
- `visuals/review/`：独立审图报告 `figure-review-<日期>.md`（日文版 `.ja.md`），每轮一份，不覆盖旧报告。

在对应阶段才创建文件，不预建空成果。仅文章模式不生成视觉；缺少生成工具时说明具体缺项，完成可做部分，不标记最终交付完整。

基础知识稿HTML使用单文件、离线可读、手机友好的排版，带章节导航及打印样式。正文与来源内容一致，区分候选知识、已确认内容、待确认事项和编辑备注。G2批准来自真实人类回复，页面展示或按钮不能自动代表确认。

完整基础知识稿采用“分类标题＋分点条列”：每点表达一个事实、职责、行动、判断或结果，可用简短加粗标签帮助定位。复杂内容按意义分组，最多两层列表；不以大段散文呈现，也不把多件事挤在一条。不删掉必要说明、条件和来源。此格式用于知识稿审阅，正式文章仍采用自然连贯、有长短节奏的文字。

交付时链接实际文章、所选视觉和知识记录，简述修订及待确认事项。定稿与公开发布分别记录，没有发布指示时保存文件即可。
